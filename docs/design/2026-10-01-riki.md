# Design Document: riki

**Author:** Scott Idler
**Date:** 2026-10-01
**Status:** Implemented (Phases 0-6; Phase 7 deploy runs after the release)
**Review Passes Completed:** 5/5 (see Review Log)

## Summary

riki is a request-time Markdown wiki server. Pages live as `.md` files in an ordinary git repo on GitHub. riki renders them on each request, and an authenticated reader can flip the same page, at the same URL, into a no-syntax WYSIWYG editor that serializes back to clean Markdown and commits on save. Commits pushed from a laptop or an agent show up in the served view without a build step.

## Problem Statement

### Background

- Tatari is evaluating Confluence replacements; Mintlify pitched "Markdown pages, WYSIWYG editor, backed by Git" at $40K-$80K/year (`obsidian/notes/2026-09-25-mintlify-documentation-platform-evaluation.md`)
- Pain stated there: PRD/tech-spec authoring is slow; Confluence and Google Docs are bad surfaces for human + AI collaboration
- Research thread (Claude session `68c08be1`) walked Mintlify, GitBook, Outline, Docmost, Wiki.js, Tina/Keystatic: none meets all of Scott's requirements at once
- Off-the-shelf tools each hit one of two walls:
  - Wall 1: true WYSIWYG editors store HTML or JSON, not Markdown
  - Wall 2: docs-as-code tools render at build time, so editing lives at a separate admin URL
- Both walls are product choices:
  - Wall 1 falls to an editor whose document model is a Markdown AST with a bounded block vocabulary
  - Wall 2 falls to request-time rendering
- Scott, same session: "I asked if it was possible, not that it already exists. could we build it and get everything I want?"

### Problem

No product gives one surface where a reader reads a page, clicks Edit, changes it in a true WYSIWYG editor, and has the change land in git as a clean Markdown diff, while commits from a laptop or agent land on that same page.

### Goals

Every goal traces to Scott's stated requirements in session `68c08be1`:

- **Git-backed:** git is the source of truth; no database holds page content
- **Markdown:** files are plain GFM that render on GitHub as-is
- **True WYSIWYG:** authors never see Markdown syntax in the browser editor
- **Wiki-like:** hierarchical pages, sidebar nav, page-to-page links, create a page from a missing URL
- **One URL:** the page you read is the page you edit; no admin route, no build step
- **Laptop commits reconcile:** a `git push` to the content repo appears in the served view

### Non-Goals

Excluded:

- Content in a database of any kind (contradicts git-backed)
- MDX or JSX components in content (breaks "renders on GitHub as-is")
- Raw HTML in pages (no clean round trip; comrak omits it at render)

Parked, with revisit condition:

| parked | meanwhile | revisit when |
|---|---|---|
| Real-time co-editing (Yjs CRDT) | optimistic 409 | 409s show up in practice |
| Full-text search | sidebar | sidebar stops being enough to find pages |
| Page history UI | GitHub history | after first deploy |
| Image upload from the editor | add images via git | after first deploy |
| Rename / move / delete in browser | via git | after first deploy |
| Front matter editing in browser | preserved byte-exact, edit via git | after first deploy |
| Permissions finer than "authenticated at the edge" | edge auth only | a multi-team deploy |
| Confluence import | none | riki is picked for a Tatari pilot |
| Malformed (non-canonical) `.md` handling: startup scan, flag, approve-to-reformat | POC assumes none exist | riki moves past POC |
| GitHub push webhook | poll | poll staleness is a complaint |
| Second identity mode (Envoy/Okta Bearer JWT, marquee `core/src/auth.rs:109-162`) | header mode only | a work deploy |

## Proposed Solution

### Overview

```
browser ──GET /a/b────────────────▶ riki ──blob at tip──▶ bare clone
        ◀──HTML + sidebar + Edit────┘                       ▲    │
browser ──POST /_riki/api/page────▶ riki ──fetch, check,────┘    │
                                          commit, push ──────────┼──▶ GitHub (canonical)
laptop / agent ──git push────────────────────────────────────────┼──▶ GitHub
                                    riki poller ──fetch──────────┘
```

Terms used below:

- **tip:** the commit at `refs/remotes/origin/<branch>` in riki's bare clone
- **good tip:** the newest tip whose nav index built without errors; this is what riki serves
- **base oid:** the blob oid of a page as the editor loaded it (null for a new page)

Shape:

- GitHub holds the canonical content repo; riki is one more git client
- riki keeps a bare clone: no working tree, so no file watcher and no dirty state
- Reads pull blobs at the good tip straight from the object DB
- Writes are optimistic: the editor sends its base oid; the push to GitHub is the lock
- N=1 vs N=2+: writes stay correct at any replica count (GitHub serializes pushes). Read freshness is not a hard bound: a laptop push appears after the next poll's fetch + publish completes, plus any wait on the repo mutex behind a save. A riki save is visible on the saving replica as soon as its 200 returns. Home deploy is N=1

### Architecture

Workspace with one flat version and one `v*` tag (marquee precedent, `marquee/Cargo.toml:1-11`):

| crate | contents | axum? |
|---|---|---|
| `core` | git store, path mapping, nav index, front matter split, render | no; an otto `core-guard` task fails if `core` depends on axum (marquee precedent) |
| `server` | `main.rs` shim, config, routes, identity, poller, templates, embedded assets | yes |

Plus `editor/`: TypeScript strict, pnpm with committed lockfile, esbuild, vitest. Output: one bundle committed at `server/assets/editor.js`, compiled into the binary with `include_bytes!`.

Components:

- **Git store** (`core`)
  - git2, default features off: blob reads, `git2::build::TreeUpdateBuilder` writes, commit creation
  - `git` CLI for `fetch` and `push`. Reasons: gix has no push; git2 network pulls libssh2/openssl and reports push rejection only via a callback (`git2/src/remote_callbacks.rs:196-206`); the CLI reuses whatever credential the host already has
  - Every CLI call: timeout from `git.timeout`, `kill_on_drop(true)`, stdout/stderr drained concurrently (`rules/rust.md:70-71`)
  - Every git2 call: `spawn_blocking`
  - One `tokio::sync::Mutex` per repo serializes fetch, push, and ref updates inside the process (two concurrent `git fetch` runs on one repo collide on ref lock files)
- **Poller** (`server`): every `poll-interval`, fetch; on a new tip, run **publish**
- **Publish** (`core` + `server`, one function, the only way the good tip moves): build the nav index for a commit; on success write the commit to the local ref `refs/riki/good` and swap the in-memory index; on failure leave both alone and record the error for the banner. Startup reads `refs/riki/good` (falls back to the tip on first run), so a restart never serves an invalid tip
- **Nav index** (`core`): one tree walk per commit into a sorted page tree plus the URL -> path map; cached by commit oid; carries index errors
- **Renderer** (`core`): comrak 0.55 with `table`, `strikethrough`, `tasklist`, `autolink`, `alerts`, `front_matter_delimiter: "---"`, `header_id_prefix: ""`; safe mode (raw HTML omitted, `javascript:` hrefs blanked)
  - `link_url_rewriter`: relative links resolve against the **source file's** directory (not the browser URL, since `/a/b` may be served from `a/b/README.md`), then map to riki URLs (`x.md` -> `/x`); absolute and external URLs pass through
  - `image_url_rewriter`: relative image paths resolve the same way, then map to `/_riki/raw/<resolved>`
- **Templates** (`server`): plain `.html` compiled in with `include_str!`, single-pass `__TOKEN__` fill (marquee `server/src/render.rs:235`); self-contained error page (marquee `lostsignal.rs` precedent)
- **Editor** (`editor/`): `@milkdown/kit` with preset-commonmark, preset-gfm, a custom alert node with its own toMarkdown handler, and stringify options picked by Phase 0a
  - The kit is headless, so riki ships its own no-syntax authoring UI on kit commands: a toolbar (heading level, bold, italic, strike, inline code, bullet / ordered / task list, quote, code block, table, alert with type picker, link) plus kit's link tooltip component for editing a link's URL
  - Markdown input rules (typing `## `) stay on as a shortcut; nothing requires them

### Data Model

URL to file mapping (GitHub's own conventions, so the repo browses the same on github.com):

| URL | file |
|---|---|
| `/` | `README.md` |
| `/a/b` | `a/b.md`, else `a/b/README.md` |
| `/a/b.md` | 301 to `/a/b` |
| `/_riki/raw/<path>` | image blobs only (`png`, `jpg`, `jpeg`, `gif`, `webp`, `svg`), served with marquee's `CSP_ASSET` (`default-src 'none'; frame-ancestors 'self'`, marquee `server/src/render.rs:91-92`) so an SVG cannot run script against the save API; other extensions 404 |

Index rules:

- `a/b.md` and `a/b/README.md` both present: index error
- Path segments: no `..`, no NUL, no leading `.`; violations are typed errors, never panics (git2 `upsert` unwraps on a NUL path)
- Reserved top-level names: `_riki`, `health`, `ready`, `status`, `deployed`, `version` (sdv probes `status`, `deployed`, `version` at the root, `sdv/src/report.rs:15`); content claiming one is an index error
- Any index error on a new tip: publish refuses it, riki keeps serving the good tip, and every page shows a banner naming the error and the offending commit. Only a commit pushed from outside riki can get here; riki validates its own commits before pushing (save step 7)

Page file rules:

- Front matter: the boundary is whatever comrak parses as front matter. riki parses the file with comrak and takes the `NodeValue::FrontMatter` text as the prefix; the body is the remaining bytes. comrak's own `split_off_front_matter` is private (`comrak-0.55.0/src/lib.rs:81`, `mod strings`), so riki reads the parsed node instead of reimplementing it. Tests assert `prefix + body == file` on adversarial fixtures: no front matter, front matter only with and without a trailing newline, a `---` thematic break in the body, an unterminated opener
- The server strips front matter before the editor sees the body. On save it re-attaches the front matter of the tip blob, which is byte-identical to the base blob's, because step 4 has already confirmed the oids match. New pages have no front matter
- **Static rules**: a file is never editable if it has non-UTF-8 bytes, a leading BOM, or any `\r`. The server enforces these on `GET /_riki/api/page` (`editable: false`) and again on save against the tip blob (422)
- **Round-trip guard**, strict: the editor's no-edit serialization of the body must equal the stored body byte for byte, trailing-newline state aside. The server does the comparison and logs every result. A page that fails stays readable and editable via git. Strict comparison is the definition of "clean Markdown" in this doc: on a page that passes, an edit's diff only touches the blocks the author changed. It also catches everything a rendered-HTML comparison misses (raw HTML, which comrak's safe mode collapses to one placeholder, `comrak-0.55.0/src/html.rs:680,731`; dropped reference definitions; style churn)
- Trailing newline: saved output keeps the original file's trailing-newline state; new pages end with exactly one `\n`

Config: `~/.config/riki/riki.yml`, kebab-case, `deny_unknown_fields`, durations via humantime. The repo ships one annotated `riki.example.yml`. No secrets in config: the push credential comes from the host's git setup (deploy key wired by `GIT_SSH_COMMAND` in the systemd unit).

```yaml
listen: 127.0.0.1:8737            # header identity requires loopback; startup fails otherwise. 8080 is taken in homelab (Caddyfile:30, searxng)
content:
  remote: git@github.com:scottidler/<content-repo>.git
  branch: main
  cache-dir: ~/.cache/riki/content.git
git:
  timeout: 30s
  poll-interval: 30s
  push-retries: 1
committer:                         # git committer; author is always the editing user
  name: riki
  email: riki@localhost
identity:
  mode: header
  email-header: Remote-Email       # required on writes
  name-header: Remote-Name         # optional; falls back to the email
```

### API Design

Reserved routes mount before the page catch-all:

| route | purpose |
|---|---|
| `GET /health /ready /deployed /version` | standard endpoints; JSON shapes copied from marquee `core/src/runtime.rs:133-170` |
| `GET /status` | marquee shape `{status, uptime[, error]}`, but unlike marquee (always `ok`, `runtime.rs:299-305`) it reports `degraded` with `error` while upstream is unreachable or the newest tip failed publish |
| `GET /_riki/assets/*` | embedded CSS and editor bundle |
| `GET /_riki/raw/{*path}` | image blobs from the good tip, `CSP_ASSET` (see Data Model) |
| `GET /_riki/api/page?path=` | `{path, base-oid, body, editable, reason}`; `base-oid` null when missing; front matter is never sent |
| `POST /_riki/api/roundtrip` | `{path, base-oid, serialized}` -> `{identical, first-diff-line}`; compares with the body of blob `base-oid`; logs path + result at INFO |
| `POST /_riki/api/page` | save |
| `GET /{*path}` | rendered page + sidebar + Edit button; missing page renders 404 with "Create this page" |

All `POST`s: `Content-Type: application/json` required (415 otherwise). A cross-origin JSON POST needs a CORS preflight that riki never answers, so this blocks form-based CSRF (marquee precedent).

Save request:

```json
{"path": "a/b.md", "base-oid": "<blob oid | null>", "body": "<markdown>", "message": "<optional, one line>"}
```

Save algorithm (holds the repo mutex from step 3 to the response):

1. 415 unless JSON; 401 unless the email header is present
2. Validate path (`.md` suffix, segment rules, not reserved); 400 otherwise
3. `git fetch`; failure or timeout: 503, no commit
4. Let `current` = blob oid at tip for `path` (null if absent); `fm` = front matter of the `current` blob (empty if absent); `new` = `fm` + body with the trailing-newline rule applied
   - `current` blob fails a static rule: 422
   - `current` == `base-oid`: continue
   - `current` blob bytes == `new`: publish the tip, 200 `{commit: null, content-present: true}` (a concurrent save or a retried request already put this exact content there)
   - otherwise: publish the tip, 409 `{current-body}`
5. `new` == `current` blob bytes: publish the tip, 200 `{commit: null}`
6. Write blob; `TreeUpdateBuilder.upsert(path)` on the tip tree; commit with parent = tip, author = user, committer = config, message = user's or `riki: edit <path>`
7. Build the nav index for the new commit **before pushing**; an index error (e.g. a laptop added `a/b/README.md` while the browser was creating `a/b.md`): 409 naming the error, nothing pushed
8. `git push --porcelain origin <commit>:refs/heads/<branch>`
   - success: set local `refs/remotes/origin/<branch>` to the commit, publish it with the index from step 7 (cannot fail), 200 `{commit}`
   - non-fast-forward: back to step 3, at most `push-retries` times, then 409
   - timeout: 503 `{retry-safe: true}`; the outcome is unknown, and a retry is idempotent through step 4's `content-present` branch
   - any other rejection (auth, protected branch): 502 with git's stderr

Every 200 path runs publish, so a 200 always means the page as saved is what the next GET on that replica renders.

Upstream unreachable during polling: keep serving the good tip with a banner "upstream unreachable since <time>"; `/status` reports `degraded`; saves return 503 until a fetch succeeds.

Editor flow:

1. Edit click: GET page JSON; `editable: false` shows the reason and a link to the file on GitHub
2. Mount Milkdown, read-only, in place of the rendered article. The URL does not change
3. Round-trip guard: serialize the unedited doc right away and POST it to `/_riki/api/roundtrip`
   - `identical: true`: the editor becomes editable
   - `identical: false`, an HTTP error, or no answer within 5s: the editor stays read-only, shows the reason and the GitHub link, and never enables Save (fails closed)
   - new pages skip the guard (nothing to compare)
4. Save: POST; on 200, re-render the article from the good tip
5. 409: the editor keeps the user's text and offers "load latest" (discards local edits after a confirm)

The guard stops riki's own editor from corrupting pages it cannot model. The server can't prove a given save went through the guard. It enforces the static rules itself, and the guard is an editor property. Neither is a security boundary: any authenticated user can push anything via git.

Content-loss bugs found (TipTap 3.31.4). The detector counts comrak-rendered features in source vs round trip. Visible text changes in 789 bodies under the best set, against 133 for Milkdown's chosen set:
- **Raw HTML is parsed through the schema, not kept.**
  - Tags the schema doesn't know are stripped (`<details>`/`<summary>` keep only their text, `<kbd>` is lost).
  - Unknown or MDX-style block tags become escaped literal text, with the markdown inside escaped too, so the links and fenced code inside them stop working.
  - HTML comments are deleted.
  - 683 bodies lose at least one comrak raw-HTML node (Milkdown: 1). 422 of the 497 bodies with `<!--` lose it.
- **Code fences are always written with three backticks.** A 4-backtick fence that wraps a 3-backtick example gets closed early. 51 of 78 such bodies change code-block structure (Milkdown: 0).
- **Empty-text links `[](url)` are dropped** (heading anchors are the common case): 26 of 50 bodies.
- **Image and link titles are written without escaping `"`.** A title containing a quote breaks the image on re-parse. One body goes from 31 images to 19.
- **The code mark excludes all other marks** (`excludes: '_'`), so code inside a link, bold, italic or strike is schema-invalid. Most of the 1767 come from this. Two consequences:
  - With no edits, `*`x`*` is serialized as `` `*x*` ``: the asterisks move into the code span, so the text changes.
  - Any schema-normalizing path (HTML reload, content check) drops the link or bold.
  - Fixed in the prototype with `excludes: ''`, priority 50.
- **Image is a block node by default**, so an image inside text is schema-invalid (110 bodies). With `inline: true`, adjacent standalone images get merged into one paragraph on `setContent`.
- **Link `autolink` (on by default) rewrites the doc on `setContent` and on edits.** It turns filename-like text such as `CLAUDE.md` into `[CLAUDE.md](http://CLAUDE.md)` (`.md` is a TLD). 31 bodies under defaults.
- Not losses, but churn: every `&`, `<`, `>` in text is entity-encoded, `__x__` becomes `**x**`, `*` bullets become `-`, `***` becomes `---`, and reference links are inlined.

## Alternatives Considered

### Wiki.js in Markdown mode
- **Description:** off-the-shelf wiki with git storage sync
- **Pros:** exists, mature
- **Cons:** database is the source of truth; its Markdown editor is source + preview; its visual editor stores HTML
- **Why not chosen:** fails git-backed and true WYSIWYG

### Tina / Keystatic over an SSG
- **Description:** WYSIWYG that commits Markdown; Docusaurus/Astro builds the site
- **Pros:** proves WYSIWYG -> Markdown works
- **Cons:** separate admin route, build step
- **Why not chosen:** fails one URL

### Otterwiki / Gollum
- **Description:** git-backed, request-time wikis
- **Pros:** closest architecture
- **Cons:** editors edit Markdown source (CodeMirror)
- **Why not chosen:** fails true WYSIWYG; also Python / Ruby

### Working tree + file watcher
- **Description:** checkout on disk, `notify` watcher reindexes
- **Cons:** dirty-tree states, watcher races, a second source of change events
- **Why not chosen:** a bare clone keyed by oid needs neither

### gix instead of git2
- **Why not chosen:** no push support (`GitoxideLabs/gitoxide` `crate-status.md`)

### Editor loaded from a CDN (esm.sh / jsdelivr)
- **Pros:** no node toolchain
- **Why not chosen:** breaks `script-src 'self'`; unpinned third-party code; flagged by the security review of the discarded prototype

### Round-trip guard by rendered-HTML equivalence
- **Description:** allow editing when comrak renders the original and the no-edit serialization to the same HTML
- **Pros:** more pages editable
- **Cons:** comrak safe mode renders all raw HTML as one placeholder (`html.rs:680,731`), so dropped or rewritten HTML is invisible; dropped reference definitions are invisible; first save reformats the whole file
- **Why not chosen:** panel round 1 found the blind spots (832 of 8244 corpus files have raw HTML lines); strict comparison has none and matches the clean-diff requirement

### Trust edits without a round-trip guard
- **Why not chosen:** Milkdown drops front matter, escapes alerts to `\[!NOTE]`, inlines reference links; silent rewrites violate "clean Markdown"
