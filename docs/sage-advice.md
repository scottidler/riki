# Sage advice

A claude.ai response on where git-as-database bites riki, filed 2026-10-02. Em-dashes recast as colons, commas, or parens; wording otherwise verbatim.

The sharpest reframing first: "git is the only database" isn't quite true today, and that gap is exactly where the pain lives. Git is your source of truth, which is great. But your nav index, search index, and redirect map are a second database: a set of materialized views over git, held in memory, rebuilt from the good tip. Git-as-truth scales beautifully. It's the materialized-view layer that bites, and every git-backed system eventually grows a cache/index tier whether it wanted one or not. So the question isn't really "does git hurt"; it's "when do the derived views stop being cheap to rebuild from scratch."

## Where git-as-database bites, by axis of growth

**More pages.** The in-memory rebuild-per-publish is O(pages) on (or adjacent to) the write path. At hundreds of pages it's noise; the nav rebuild and search tokenization are microseconds-to-milliseconds. Somewhere in the low-thousands you'll feel it, and by tens of thousands a full-corpus reindex on every save is seconds, which stalls serving the new tip or the ack to the editor. Search forces the issue first, because re-tokenizing the whole corpus per publish is the heaviest view. This is the point where you rejected Tantivy "for now" and the real work becomes incremental indexing: update only the blobs the commit touched. That's harder than it sounds because moves, deletes, and redirects each have to mutate the index correctly, and you index the good tip, not the push. Rename-detection for redirects has the same shape: your 5,000-commit cap bounds steady state but it's also a correctness ceiling (a page moved 5,001 commits ago gets no redirect) and a cold-start tax: a fresh replica pays the full scan before it can serve.

**More editors.** Your write lock is GitHub's ref update, and that's genuinely elegant: a non-fast-forward rejection is a free, linearizable compare-and-swap on the ref, shared across every replica with zero coordination infra. That's the best feature of the design, not a liability. The cost is that it's one CAS for the whole branch: every write serializes globally regardless of which page. At low write rates, invisible. As editors climb, disjoint-page edits still have to fetch-rebase-retry because any concurrent push invalidates your fast-forward, and the window for someone to slip in during your fetch widens with N: classic optimistic-concurrency retry amplification. It won't livelock at wiki write rates, but the 409-on-same-page UX is the thing that stops being acceptable the moment it's a shared tool. You have the base blob ID the editor loaded, so the pragmatic next step is a real three-way merge server-side (git merge-tree over base + both sides) and only 409 on true textual conflict. That's a large UX win git actually hands you. Yjs is the trap: CRDT state isn't a Markdown file, so real-time co-editing fights "Markdown is canonical, every save is a commit" at the root.

**More than one replica.** Writes are fine: the shared ref is your lock. Reads are the weak axis. Each replica independently fetches, independently decides the good tip, independently holds its views, so you get a staleness window bounded by fetch cadence and N× memory and N× rebuild cost. There's no invalidation push, so you're polling GitHub on a timer (more API load, more lag). The fix is webhook-driven invalidation, which reintroduces the infra you were avoiding. And if permissions ever land, a view built naively from the good tip indexes everything: search will leak titles and snippets of pages a reader can't access, on every replica.

The place git actually hurts most is still parked: binary/image upload. Text deltas beautifully; binaries don't, and every edit bloats the pack permanently, dragging gc, clone, and fetch times up forever. That's the fork in the road: you either accept unbounded repo growth, or move blobs to LFS/S3 and break "git is the only database." You already run S3 for marquee, so the escape exists, but it's the decision that ends the purity.

## Hard parts still ahead for riki specifically

**Tables through the byte-identity guard.** GFM table round-tripping is the classic serializer-drift source (alignment rows, cell padding, pipe escaping), and ProseMirror's table model doesn't preserve any of that for free. This is where the 66-fixture guard starts forcing real pages read-only, and it's on your Mintlify-editor-feature path.

**Folder moves.** This is the stress test of the whole multi-op-commit machinery at once: N pages move, M _order files change, a redirect per moved path, and every inbound link across the corpus needs rewriting or redirecting: an O(corpus) operation most wikis get wrong. Referential integrity is the thing git gives you zero help with; atomic tree writes aren't the same as link integrity, and your good-tip gate catches index-build failure, not link-rot.

**The work deploy.** Okta JWT isn't the hard part; it's that going multi-user activates permissions, concurrent-edit UX, and search-ACL simultaneously. Several parked items stop being optional in the same quarter.

If I had to name the single highest-leverage next move: server-side three-way merge on save. It converts your biggest multi-user UX liability into a feature, and git is already handing you everything you need to do it.
